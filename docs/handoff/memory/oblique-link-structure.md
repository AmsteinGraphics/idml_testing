An oblique link = TWO sources on ONE destination (see resolve_xref.py, and [[toolchain-pivot]] Phase 3):

1. **Underlined word** in body text — a `<CharacterStyleRange AppliedCharacterStyle="CharacterStyle/link"` (or `link_slant`) containing a `<HyperlinkTextSource>` wrapping the word's `<Content>`. Bound by a `<Hyperlink Source=<src self> DestinationUniqueKey=<key>>` in designmap.xml to a destination anchor.
2. **Margin number** — a `<CrossReferenceSource AppliedFormat=<fmt>>` whose cached `<Content>` is the target's paragraph number (e.g. "5.4.6"). It lives in its OWN tiny story: `<ParagraphStyleRange AppliedParagraphStyle="ParagraphStyle/cross_ref_par"><CharacterStyleRange AppliedCharacterStyle="CharacterStyle/code_styles:cross_ref"><CrossReferenceSource…>`. Format is one of `dm32_cross_ref` / `dm32_cross_par` (CrossReferenceFormat in designmap). Also bound by a `<Hyperlink>` to the same destination key.

**The margin box is an ANCHORED object, not a spread frame.** The margin story is rendered by a `<TextFrame AppliedObjectStyle="ObjectStyle/cross_ref_block" ParentStory=<margin story>>` that is embedded INLINE inside the underlined word's `CharacterStyle/link` range in the BODY story (verified: every CrossReferenceSource story is referenced by ParentStory inside a body story, never by a spread). No per-frame AnchoredObjectSetting — margin placement comes from ObjectStyle `cross_ref_block`. So generation needs NO composition geometry: insert the anchored frame at the word, InDesign positions it.

Destinations: `<HyperlinkTextDestination DestinationUniqueKey=<key> Name=… >` (named anchor on a heading) or `<ParagraphDestination>`. Page-anchor/TOC links (dest_key resolving to page/0) are NOT oblique links.

FORWARD generation (submission has underlined word + its Hyperlink→dest, NO box): for each such link create a margin story (cross_ref_par + code_styles:cross_ref + CrossReferenceSource, format dm32_cross_par, Content=target number placeholder — InDesign refreshes on open), insert an anchored cross_ref_block TextFrame into the word's link range, add a `<Hyperlink>` binding the new CrossReferenceSource → same dest key, register the margin story in designmap (idPkg:Story + StoryList).

ORACLE / round-trip dev strategy: test1 already CONTAINS the boxes (14 complete links). Strip boxes → boxless "submission"; regenerate; diff against original. Object style used: `cross_ref_block`; margin para style `cross_ref_par`; margin char style `code_styles:cross_ref`; box has CornerRadius=12, FillColor Swatch/None.

ROOT CAUSE + DESIGN (user-confirmed 2026-08-05): section numbers are meant to be LIVE multi-level auto-numbering, NOT text. Paragraph styles titles:lvl2/lvl3/lvl4 = levels 1/2/3 of NumberingList `dm32_list`, NumberingExpression ^1 / ^1.^2 / ^1.^2.^3 (chapter 5 → 5.1 → 5.1.1). With numbering ACTIVE, the ParagraphNumber cross-reference resolves correctly and margin boxes populate. test1 (and v1.76 as shipped) are in a FLATTENED state: a destructive PRE-PRINT step converts live numbers to literal text + switches numbering off on instances (BulletsAndNumberingListType="NoList") — that is why xrefs resolve to empty there. The user flattens manually via InDesign (script variables_to_text.jsx + GREP) only at PDF-export time on a backup; it also bakes tab numbers via text variable `dm32_foot_thread` (matches paragraph style, running section thread) and footer threads. So: a real toolchain SUBMISSION is in AUTHORING state (numbering active); test1 is a poor oracle for xref RESOLUTION because it is pre-flattened. Currently only titles:lvl4 pins AppliedNumberingList=dm32_list; lvl2/lvl3 carry NumberingLevel+NumberingExpression but would need dm32_list applied + BulletsAndNumberingListType=NumberedList to be active. SCOPE DECISION (user 2026-08-05): SUBMISSIONS ARE PRE-NUMBERED — the toolchain ASSUMES active dm32_list numbering on titles:lvl2/3/4 and just generates xref boxes on top; it does NOT activate/un-flatten numbering. Consequence: test1 is a poor oracle for xref RESOLUTION (it is flattened). Need an AUTHORING-STATE (pre-flatten, active-numbering) test file to validate that generated boxes populate. The empty panel/boxes seen on test1-derived files are most likely the flattened state (unresolved ParagraphNumber xrefs don't display), not necessarily a generation bug — re-validate against an active-numbering file before further debugging build_xref_boxes.

CRITICAL — NUMBER RESOLUTION (discovered 2026-08-04): the margin-number formats `dm32_cross_ref` (u1520) AND `dm32_cross_par` (u1521) both use a single `ParagraphNumberBuildingBlock`. BUT every DM32 heading types its section number as LITERAL text (e.g. Content "7.2.1 One-number functions") with NO list numbering (paragraph style titles:lvlN has no NumberingList). A Paragraph-Number cross-reference reads a LIST number → none exists → resolves to EMPTY. This is true in v1.76 too (not a copy-paste artifact). Therefore the whole margin-number system runs on CACHED values baked into `<CrossReferenceSource><Content>NN</Content>`: v1.76 boxes carry cached "21"/"21.1" etc.; InDesign DISPLAYS the cache but blanks it on manual Update Cross-Reference (confirmed by user on test1). Consequence for the toolchain: a live Paragraph-Number xref cannot produce these numbers. Open question with user: keep xrefs but set correct cached numbers (extracted from target heading leading token) / switch to a text-extraction format / use static text. Also unresolved: machine-generated file shows EMPTY panel+boxes while test1 (InDesign-exported, identical triple structure) shows cached numbers — suspect InDesign re-resolves machine-authored xrefs on import (→empty) but trusts its own exports; isolate via manual_template_test1_xref_only.idml (strip+build_xref only, no sections/tabs).

PIVOT — BOXES VIA JSX, NOT IDML (2026-08-05, after exhaustive failure): hand-authored IDML anchored margin boxes DO NOT bind in InDesign on import — the frame imports as an empty, unlinked text frame (symptom: real text frame, paragraph cross_ref_par, but empty; typing gives character style `link` from the anchor context, not the story's code_styles:cross_ref). Verified against v1.76 (which renders): matched frame, story, registration, StoryList/idPkg:Story, DOMVersion, wrapping (frame inside word's link range, before HyperlinkTextSource), kept ParentInterfaceChangeCount (all 56 real boxes share one value), version (test1=21.3, test2=20.0, v1.76=21.4 — version-matched attempts still failed). The ONLY residual diffs were id values + idPkg:Story declaration order (original: anchored story AFTER body story; generator prepends). Conclusion: InDesign builds the frame↔story anchor binding through its DOM; IDML surgery can't reconstruct it. SOLUTION: `place_xref_boxes.jsx` creates the boxes NATIVELY in InDesign (REBUILD-on-rerun: deletes all cross_ref_block anchored frames + dangling xref hyperlinks, then recreates). It is SELF-CONTAINED — walks the doc's underlined-word hyperlinks (source HyperlinkTextSource styled `link` → HyperlinkTextDestination), creates an anchored frame (object style cross_ref_block) at each word, and adds a LIVE cross-reference (format dm32_cross_ref) to the word's destination; InDesign computes the number (no data file needed). Toolchain role: `build_xref_boxes.py --jsx` suppresses dead links in IDML (that WORKS) + logs; boxes deferred to the JSX. Full flow: sectionize → apply_tabs → build_xref_boxes --jsx → open in InDesign → run place_xref_boxes.jsx. NOTE: apply_tabs.py tab-number digits are anchored/placed similarly — MAY have the same empty-frame issue (unverified); if so, move tab-number placement to JSX too. JSX API (crossReferenceSources.add, ip.textFrames.add for anchored frame) is untested — first user run will surface errors to fix.

CRITICAL — v1.76 ANCHOR STRUCTURE (2026-08-05, after cloning from test1 gave empty/unlinked frames): the authoritative box structure is in v1.76, NOT test1 (test1 was copy-pasted, its box wrapping differs). In v1.76 the anchored box frame is the FIRST child of the SAME `<CharacterStyleRange AppliedCharacterStyle="CharacterStyle/link">` that holds the underlined word — frame THEN HyperlinkTextSource, one range. A range containing ONLY a lone frame (no text) leaves InDesign unable to bind frame→story (symptom: box is a real text frame, correct paragraph style cross_ref_par, but EMPTY; typing in it inherits `link` char style from the anchor context instead of showing the story's code_styles:cross_ref content). FIX in build_xref_boxes.py: insert the frame at the HyperlinkTextSource's start position (mm.start()) so it becomes the source's previous sibling inside the open range. Also: ids MUST be lowercase-hex u<hex> (uppercase uXB/uCM ids also break the anchored frame→story link — likely affects apply_tabs.py tab-number stories too, verify tab digits render). Templates now re-extracted from v1.76 (box_frame.xml = frame u36047; margin_story.xml = story u12346, number 5.3.1). GUARD: some HyperlinkTextSources are index entries (carry a <PageReference>, sit directly under the paragraph preceded by an empty self-closed <CharacterStyleRange link/>) — inserting there orphans the frame; skip+log them (reason=complex-source-structure). test2 static: 22 boxes well-formed, 4 skipped, 30 dead suppressed. AWAITING InDesign confirmation that boxes now render.

CRITICAL INSERTION RULE (bug fixed 2026-08-04): the anchored box frame must be emitted as its OWN complete `<CharacterStyleRange AppliedCharacterStyle="CharacterStyle/link"><TextFrame …box…/></CharacterStyleRange>` placed as a SIBLING immediately BEFORE the underlined word's own CharacterStyleRange — exactly how InDesign structures it (box range, then word range, both style `link`). Inserting the frame *inside* the word's range (after its opening tag) malforms the nesting (word CSR came out self-closed, frame orphaned) → InDesign can't bind the CrossReferenceSource anchor → cross-reference unresolved → EMPTY box + EMPTY Cross-References panel. Symptom to watch for. Also note: inner-margin placement of the box is CORRECT by design (not a bug).
